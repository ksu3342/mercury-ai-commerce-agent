# Mercury 面试防守手册

这份文档用于面试答辩。回答风格建议是：先讲问题本质，再讲系统边界，最后讲工程兜底。不要把 Mercury 讲成“万能自动合规平台”，而要讲成“可审核、可追踪、可评估的多语言内容发布 Agent”。

## 1. 为什么这个场景需要 Agent，而不是普通脚本？

普通脚本适合固定输入、固定规则、固定输出。Mercury 的流程是多步、有状态、有分支的：先结构化商品资料，再检索规则和术语，再生成多语言 Listing，再做合规校验，再进入人工审核，最后导出。中间任何一步都可能改变下一步，比如发现 EU 市场缺少负责人字段，就不能直接发布，而要进入修复或人审。

所以这里的 Agent 不是“让模型自由发挥”，而是一个受控 workflow graph。LLM 只负责语言生成、属性解释和修复建议，流程控制、校验和发布边界由工程系统掌握。

## 2. 这个项目和普通跨境电商文案生成工具有什么区别？

普通工具的核心是生成文案，Mercury 的核心是受规则约束的内容发布。它不仅生成标题、卖点和详情，还会检索规则、保留证据、执行 deterministic validators、输出 ComplianceReport、记录人工审核结果和评估指标。

一句话说：文案生成只是一个节点，真正展示的是多语言内容生成、规则校验、人审闭环和可观测评估的 Agent 系统。

## 3. 如何减少模型幻觉？

我分三层处理。

第一层是检索约束：规则、品牌术语、历史优秀文案都通过 retriever 提供，生成结果要带 `retrieved_chunks`。第二层是结构约束：LLM 输出必须符合 `GeneratedListing` schema，不接受不可解析的自由文本。第三层是执行约束：敏感词、必填字段、单位、标题长度、风险声明由规则引擎和确定性 validator 检查。

关键原则是：不能只靠 prompt 要求模型“不要幻觉”，必须用系统设计限制它产生不可控输出。

## 4. RAG 在这里的作用是什么？

RAG 的作用不是让文案更长，而是给模型提供可追溯的业务上下文。Mercury 检索三类内容：平台规则、品牌术语、历史优秀文案。

平台规则用于减少编造合规要求；品牌术语用于保证翻译一致；历史优秀文案用于学习表达风格。每次生成都记录 `retrieved_chunks`，面试官追问“依据是什么”时可以回到具体片段。

## 5. 为什么有 RAG 还需要规则引擎？

RAG 提供知识，规则引擎负责判断。二者解决的问题不同。

例如 RAG 可以检索到“EU 市场需要 responsible person”，但最终某个 Listing 是否缺少字段，应由确定性规则判断，而不是让模型猜。合规、单位、长度、必填字段这些必须稳定可复现，不能交给概率模型。

## 6. 为什么还需要人工审核？

因为当前系统定位是 Portfolio PoC，不是法律意义上的自动合规平台。LLM 和规则引擎可以提前发现大量显性问题，但最终发布内容仍涉及品牌、法律和平台政策风险。

人工审核的价值不只是兜底，还会产生评估数据：哪些字段被修改、修改率多少、哪些规则误报或漏报。这些数据会反过来改进 prompt、规则和评测集。

## 7. 如何评估生成质量？

我不用单一“模型打分”。Mercury 分四层评估：属性完整率、合规问题 precision/recall、人工修改率、多语言质量 rubric。

属性完整率看是否满足发布字段；precision/recall 看合规检查是否可靠；人工修改率看运营是否真的省时间；多语言 rubric 看语义保真、术语一致、本地化和合规语气。这比单纯 BLEU、ROUGE 或模型自评更贴近业务。

## 8. 没有真实 Shopify、Google Merchant、Amazon API 接入，会不会被质疑？

会被问到，但这不是硬伤，前提是边界说清楚。Mercury 是 Business Simulation PoC，当前阶段不接真实平台 API，只做 Adapter 接口和 Shopify-like payload。

我会解释：真实 API 接入的难点主要是账号、权限、限流、字段映射和平台变更；但这个项目要证明的是 Agent 核心链路，即生成、检索、校验、审核、评估和导出。Adapter 边界保留后，真实接入是后续工程替换，不改变核心架构。

## 9. Mock 数据和真实系统差距在哪里？

差距主要在三点：真实商品数据更脏，真实平台规则更多且变化更频繁，真实 API 会有鉴权、限流和错误码。

Mercury 的 Mock 不是假装真实，而是用于隔离核心问题。为了缩小差距，Mock payload 会模拟真实字段结构，规则包会版本化，失败案例库会保留脏数据样本，Adapter 层会明确输入输出边界。

## 10. 如果规则变更怎么办？

规则不写死在代码和 prompt 里，而是作为 `PolicyRule` 和 `policy_version` 管理。规则变更后，更新规则包并跑回归评估，重点看 blocker recall、precision 和历史失败案例是否受影响。

我不会回答“换个 prompt 就行”，因为平台规则属于业务配置和校验逻辑，应该版本化、可回滚、可审计。

## 11. 如果模型输出错误怎么办？

先判断错误类型。如果是格式错误，JSON Schema 拦截；如果是字段缺失，deterministic validator 拦截；如果是合规问题，rule engine 拦截；如果是语言质量问题，人工审核记录并进入评估集。

错误不会直接发布。系统会记录 `trace_id`、`prompt_version`、`retrieved_chunks`、`validator_result`、`human_review_result`，用于复现和修复。

## 12. 如何避免过度工程化？

我把 v1 限制为最小闭环：FastAPI、PostgreSQL 设计、Mock retriever 或 FAISS、显式 workflow graph、Mock export adapter。Milvus、OpenTelemetry、Prometheus、真实平台 API 都是预留替换点，不是 v1 必做项。

过度工程化的风险是为了炫技堆组件。Mercury 的每个模块都对应明确问题：RAG 控制知识边界，规则引擎保证确定性，人审控制发布风险，可观测保证复盘。

## 13. 为什么选 FastAPI？

FastAPI 适合这个 PoC，因为它能快速表达 API 合同、Pydantic schema 和 OpenAPI 文档。面试时可以直接展示接口，而不是只展示脚本输出。

如果生产化，FastAPI 也能平滑接入任务队列、数据库、认证和监控。它不是为了流行，而是匹配“API-first 的 Agent 服务”这个目标。

## 14. 为什么数据库设计为 PostgreSQL？

Mercury 需要存 run、listing、compliance report、review、policy version、trace metadata，这些是关系清晰、需要查询和审计的数据。PostgreSQL 足够稳定，也方便后续做 JSONB 字段存储半结构化结果。

PoC 可以先用文件或 SQLite，但设计上按 PostgreSQL 是为了表达真实后端边界。

## 15. 为什么 v1 可以用 Mock retriever 或 FAISS，而不是直接 Milvus？

因为 v1 样本规模小，重点是验证检索接口、上下文注入和引用回溯，不是验证大规模向量检索性能。FAISS 或 Mock retriever 足够演示。

Milvus 是后续规模化替换点：当规则片段、历史文案和多语言语料增长到需要服务化检索时，再切 Milvus 更合理。

## 16. 如何设计 LLM Provider 抽象？

Provider 接收结构化请求：prompt version、输入对象、期望 schema、temperature 和 trace context。返回结构化 JSON、模型名、token 用量、延迟和错误信息。

这样做的好处是模型可替换。无论用 Qwen、OpenAI、Claude 或本地 vLLM，业务层不直接依赖具体 SDK。

## 17. 为什么不让 Agent 自动发布？

因为发布是高风险动作。PoC 阶段只导出 CSV / JSON / Shopify-like payload，不直接调用真实平台 API。

这不是保守，而是正确的责任边界。系统可以生成可发布草稿和风险报告，但最终发布前应由人审确认。等权限、审计、回滚和告警完善后，才考虑真实发布。

## 18. 图文一致性怎么做？

v1 可以先做轻量版本：图片 URL、alt text、Mock OCR 文本和商品属性做一致性检查。例如 OCR 出现“600ml”，但属性是 `capacity_ml=450`，就标记 warning。

如果后续接多模态模型，可以让 VL 模型提取图片文字、颜色、包装声明，再交给 deterministic validator 对比。关键是多模态结果也不能直接作为事实，仍要进入校验。

## 19. 如何处理敏感词和夸大宣传？

敏感词分两层。第一层是确定性词表，例如 `100% safe`、`cure`、`guaranteed` 这类高风险表达。第二层是语义风险，例如暗示医疗功效或绝对化安全承诺，这部分可以用 LLM 做候选识别，但最终规则报告要给出证据和人工确认入口。

我不会承诺 100% 识别所有敏感表达，所以用 precision/recall 和失败案例库持续迭代。

## 20. 如何证明系统可迁移到其他行业？

把电商词汇拿掉，底层模式仍然成立：输入资料结构化、检索规则和术语、生成受约束内容、确定性校验、人工审核、导出到目标系统。

内容平台可以用它审核多语言文章，广告平台可以用它生成素材并检查政策，SaaS 可以用它生成帮助文档并校验术语，企业 Agent 可以用它发布内部知识。

## 21. 面试官问“你这个是不是套壳 LangGraph”怎么回答？

我会说：LangGraph 风格只是编排方式，不是项目价值本身。Mercury 的重点是状态如何设计、每个节点的输入输出是什么、失败如何恢复、哪些判断交给模型、哪些交给规则系统。

即使用自己实现的 workflow graph，只要状态、节点和可观测边界清楚，架构仍成立。

## 22. 如何处理多语言术语一致性？

品牌词、材料名、类目词进入 terminology memory。生成时检索目标语言术语，校验时检查品牌词是否被翻译、单位是否符合市场配置、关键属性数值是否一致。

例如品牌 `Mori` 不应翻译，`Tritan` 不应被改写为普通塑料。术语一致性不是语言模型自由决定，而是可校验约束。

## 23. 如果 RAG 检索错了怎么办？

检索错会导致生成依据错，所以需要记录 `retrieved_chunks` 并评估 retrieval quality。v1 可以人工抽查 top_k 片段；后续可以加入 rerank、规则类型过滤、市场过滤和 chunk 版本。

如果校验发现模型使用了不相关规则，失败案例记录为 `retrieval_miss` 或 `retrieval_noise`，再优化检索配置。

## 24. 如何设计失败重试？

重试不能盲目重新生成。Mercury 会根据失败类型选择动作：schema 格式错误可以要求模型按 schema 修复；缺少必填字段则提示用户或填入 Mock 责任主体；合规 blocker 则进入人工审核；语言质量差可以带审核意见重生成。

这体现 Agent 的价值：根据中间结果选择下一步，而不是固定脚本从头跑。

## 25. 如何向 HR 或非技术面试官解释项目价值？

我会说：跨境商品上新不是简单翻译，而是要同时满足目标语言、平台字段、合规规则和品牌表达。Mercury 把原本多轮人工处理的流程压缩成“可复核草稿 + 风险报告”，让运营从重写内容变成审核和修正重点问题。

这句话适当营销，但不夸大。它强调的是提效和风险前置，不承诺替代人或保证平台一定通过。

## 26. 如何向技术面试官解释项目亮点？

我会强调四点：第一，workflow graph 明确控制 Agent 状态；第二，RAG 提供可追溯上下文；第三，规则引擎和 deterministic validators 接管必须正确的判断；第四，可观测和离线评估让系统能持续改进。

这比“调用一个模型生成文案”更接近真实 LLM 应用系统。

## 27. 如果用户输入很少，系统怎么处理？

系统先输出 `missing_attributes`，并把缺失字段按市场和严重程度分级。如果字段是可建议的，比如 SEO keywords，可以让模型补；如果字段是事实属性，比如电池容量、材质、认证、负责人，不能让模型编。

原则是：事实缺失必须暴露，表达优化可以生成。

## 28. 如果平台最终仍然拒登怎么办？

这说明规则库或校验器没有覆盖真实平台判断。系统会把拒登原因作为新的 `PolicyRule` 或失败案例输入，更新规则包并跑回归。

我不会说系统能完全避免拒登。更可信的说法是：它能提前拦截常见错误，并把拒登反馈转成可迭代数据。

## 29. 如何处理成本和性能？

v1 记录 token usage、latency_ms 和每个节点耗时。成本优化顺序是：先减少无效重生成，再缓存检索结果，再把确定性逻辑从模型里移出去，最后才考虑换更便宜的模型。

性能口径只作为 MVP 验收目标，不声称线上结果；建议目标是单 SKU 草稿生成 p95 < 20 秒，用于判断 Demo 交互是否顺畅。

## 30. 最容易被击穿的问题是什么？怎么防？

最容易被击穿的是把系统讲成“自动合规”。因为合规是法律和平台共同决定的，不可能由 PoC 保证。

防守方式是明确边界：Mercury 做合规预检、风险分级、证据记录和人工审核，不替代法务或平台最终审核。这个边界清楚后，项目反而更可信。

## 31. 如何用一句话总结 Mercury？

Mercury 是一个多语言内容发布 Agent：它用 RAG 给模型提供规则和样例，用结构化 schema 管住输出，用规则引擎识别风险，用人工审核形成闭环，用 trace 和评估指标证明每次生成可追踪、可改进、可防击穿。
